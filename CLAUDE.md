# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Predictive maintenance for Malaysian telecom towers. Built for ASEAN GeoAI Fusion 2026 hackathon (Innovation track). Full narrative in `docs/Concept_Overview.md`. Three-stage arc:

```
detect                    decide                      dispatch
Tower Health Risk Index → Action + urgency          → Crew schedule
(ML, unsupervised,         (dominant risk factor       (greedy optimizer,
 physics-based)             -> work order + SLA)        constraints, agent overlay)
```

- **Layer 1 — Risk Index** (`src/backend/model/`): score every tower 0-1, plus uncertainty band and per-factor attribution (flood, terrain, lightning, equipment, power). Not failure predictor — no failure labels exist anywhere in project, code must not imply one (see `docs/Backend_Handoff.md` §0.6).
- **Layer 2 — Scheduler** (`src/backend/scheduler/` + `agent/`): turn `dominant_factor` + `urgency_days` into work orders. Greedy solver packs them into crew-days under territory/depot/crew-type/SLA/monsoon constraints. **Optimizer decides; LLM never emits schedule** — agent only calls tools, reports return values verbatim.

`docs/Backend_Handoff.md` = authoritative spec for scheduler/agent/API surface — read before touching `src/backend/scheduler/`, `agent/`, or `api/`. `docs/ML_Implementation_Plan.md` covers risk-index phases (perception, membership curves, AHP weights, attribution, rank-stability validation).

Training lives in the notebook; serving lives in `model/maintenance_need.py`. The
module owns every shared constant (`FEATURES`, `FACTOR_GROUPS`, `PARAMS`, artifact
paths) and the notebook imports all of them — never redefines its own copy. A
notebook that declared its own `FEATURES` would train a model the API then feeds
different columns to, in a different order, and LightGBM accepts a positional
array without complaint: nothing raises, the numbers are just wrong.
`model/test_maintenance_need.py` parses the notebook's cell source as an AST and
fails the build on any redefinition.

The last three need `pip install -r src/backend/requirements-dataset.txt` (scipy,
matplotlib, pyshp, scikit-learn). All three cache every HTTP response under
`data/malaysia/cache`, so a re-run is free; the first full run is ~2 h, dominated
by 41 Overpass tiles. **Never point a `--limit` smoke run at the real cache
directory** — it writes a partial `hand_samples.json` that a later full run reads
back, which silently produced a 97%-smaller dataset once; `fetch_hand` now raises
above 5% missing rather than reporting it as a drop count.

### Frontend (`src/frontend/`, React + TypeScript + Vite)

```bash
cd src/frontend
npm install
npm run dev       # Vite dev server
npm run build      # tsc -b && vite build
npm run lint       # oxlint
npm run preview
```

**A fresh clone needs no `.env` at all, and `VITE_API_BASE` should stay UNSET.** The browser talks only to Vite's own origin: `api/client.ts` defaults `API_BASE` to the relative `/api` and `vite.config.ts` forwards that to the backend. One origin, so there is no preflight, no CORS header to be rewritten in transit, and no `localhost`-vs-`127.0.0.1` / IPv4-vs-IPv6 mismatch to fall into. Setting `VITE_API_BASE` to an absolute URL **opts out of all of it** — the browser goes straight to the backend cross-origin and the proxy stops being involved. That is right for a deployed backend and wrong locally, and it has already cost real time twice: once as an IPv6 lookup failure that silently served fixtures while looking live (where `localhost` resolves to `::1` first — the macOS default — the browser gets `::1` and finds nothing, because uvicorn's default bind is IPv4-only; `curl` keeps working by falling back to IPv4, so it reads as a frontend bug for an hour, and `uvicorn --host ::` is NOT the fix — measured, it binds IPv6 *only* and breaks the IPv4 side), and once as a proxy that looked broken because a leftover absolute `VITE_API_BASE` meant nothing was going through it.

**The knob is `VITE_PROXY_TARGET`, default `http://127.0.0.1:8001`.** 8000 is the default for uvicorn, FastAPI and Django and so the most contested port on a developer machine; when something else holds it, requests reach a stranger's API and return 404 rather than refusing, which is slower to diagnose than a dead port — hence 8001, and hence `--port 8001` on the bare `uvicorn` line above. `vite.config.ts` reads that variable from the process environment **and** from `src/frontend/.env`, in that order. The `.env` half had to be added: Vite loads `.env` files into `import.meta.env` for client code and never into `process.env` for the config, so a developer writing `VITE_PROXY_TARGET` into the obvious place got no proxy change and no error — which is precisely why a `.env` carrying an absolute `VITE_API_BASE` existed in the first place. Process env still wins over the file, so `make dev BACKEND_PORT=8000` is not swallowed by a developer's `.env.local`. `make dev` pins both ends (`BACKEND_HOST`/`BACKEND_PORT`/`API_BASE`), and `make stop` tears down only this checkout, matching the backend on `api.main:app` and the frontend on `$(CURDIR)`'s own vite path rather than on whoever holds the port. `make install` installs all four requirements files: `requirements.txt` alone boots the API but silently serves the physical index, because lightgbm *and* scikit-learn both sit on the serving path.

**No test script in `package.json`** — `lint` is oxlint, `build` is `tsc -b && vite build`. Verify UI work with `build` + `lint` plus browser check; do not claim visual, accessibility, or map-rendering change verified on passing build alone. `npm run build` cannot catch MapLibre worker bug below — dev-only.

There are **sixteen** real test files — every dependency-free `lib/` module — and their invocation
is not obvious:
```bash
cd src/frontend
for f in src/lib/*.test.mjs; do node --experimental-strip-types --test "$f"; done
# agentEvents 9 · crewOptions 15 · crewPosition 7 · dispatchAnimation 5 · dispatchImpact 10
# gantt 9 · inundation 1 · readiness 7 · ticketSuggestion 8 · ticketUrgency 9
# coverageGeometry 11 · responsePhaseGeometry 9 · simulationClock 13 · simulationConsoleLine 7
# simulationSummary 9 · simulationTimeline 14 = 143
```
They use `node:test` and import the `.ts` module directly. **Plain `node --test` fails** with
`ERR_UNKNOWN_FILE_EXTENSION` — the strip-types flag is what makes it run (Node 22). This is the
pattern to copy for any other dependency-free `lib/` module worth testing.

**A tested `lib/` module's VALUE imports need explicit `.ts` extensions; its type-only imports must
not.** Node's ESM resolver will not infer an extension, so `import { x } from './y'` throws
`ERR_MODULE_NOT_FOUND` under the test runner while compiling and bundling perfectly well —
`tsconfig.app.json` sets `allowImportingTsExtensions` with `noEmit`, and Vite is indifferent. This
only bites modules that import another local module: `inundation.ts` never hit it because its one
import is `import type`, which is erased before resolution. `ticketSuggestion.ts` carries the
extensions and a comment saying why; do not "tidy" them away.

## Architecture

### Backend layout (`src/backend/`)

**`risk` is the index itself, and the classifier that used to stand in front of it was withdrawn.** `adapter/ml_source.py` computes risk and attribution by calling `model/risk_index.py` over `tower_feature_table.csv` — one input, no CSV of pre-scored decisions. The removed `maintenance_classifier` reported 0.974 out-of-fold AUC, which was arithmetic rather than evidence: its label was a quantile cut on `technical_risk`, itself a deterministic function of the same six features the model was given, so it was scored on its ability to invert a monotone threshold it had been handed. Its own metadata said the target was "policy-generated, not observed maintenance outcome". Three things went with it — the `model_policy_disagreement` badge (no classifier, no disagreement to show; it was read through a TypeScript cast in three components, so `tsc` would **not** have caught its removal), the `risk_lo`/`risk_hi` ratio correction (only needed because risk and the perturbation draws were on different scales), and `_three_band_decision`'s override argument. `/towers` and `/score` now return risk on the same scale, which they did not before — `useLiveTowers` switches between them the moment a weight slider leaves baseline. The index is genuinely compressed on this AOI (p50 ≈ 0.95, IQR 0.10, median HAND 1.12 m); that is a true property of flat low-lying ground, stated on the Method page, and it is why the decision bands are cut by quantile rather than at fixed thresholds.

**The live forecast enters at urgency, never at risk — two seams, deliberately.** The risk index is the standing, slow score of maintenance *need*; `validate.py` exists to prove its ranking is stable under weight perturbation, and feeding a 3-hourly soil-moisture reading into it would reshuffle that ranking several times a day and make the claim meaningless. A score that visibly tracks the weather also reads as a failure predictor, which `docs/Backend_Handoff.md` §0.6 forbids. So `scheduler/urgency.py` is the only place weather lands: `flood/forecast.py` samples GFS 24 h rainfall and SMAP soil moisture at the tower points and returns a multiplier that shortens **only** the factors in `policy.yaml`'s `weather_hazard.coupled_factors` (flood at 1.0, terrain at 0.5). Rain does not accelerate radio-unit wear-out, so an equipment-dominant tower's 90-day refresh must not move — pinned by `scheduler/test_urgency.py`. Because the multiplier lands on the base timescale before the share weights it, the shift is proportional to flood exposure: measured live, a 0.98-flood-share tower went 11→9 days while a 0.10-share one went 37→35. Four rules hold it in place. It **only shortens** (clamped ≤1.0 — a dry forecast is not evidence of safety, and lengthening an SLA on a three-day model run is the one move that could damage a site). It has a **floor** (`min_multiplier`, or one storm collapses every flood-dominant tower onto the same date and the optimizer's ordering goes flat). It is **off by default**, because a live forecast makes a run non-reproducible — the same reason `demo_clock.today` is pinned. And unavailable is **`None`, never a multiplier of 1.0**: `weather: null` means "we could not ask", `{multiplier: 1.0}` means "we asked and it is quiet", and the UI must not conflate them. GloFAS is excluded on purpose — it is river-basin discharge return period, so sampling a basin polygon at a tower's coordinates and calling that the tower's hazard is a category error. `scheduler/` imports neither `flood.forecast` nor `earthengine-api`; the hazard is duck-typed on `.multiplier`, which is what keeps `/schedule` working with no credentials.

**The one supervised model here learns from a label nobody in this project generated, and it returns null.** `model/signal_performance.py` asks whether site environment explains measured RSRP once geometry is controlled, over a panel built by `data/prepare_signal_panel.py` from 30,925 operator drive-test measurements. Held-out R² with `GroupKFold` on the physical site: null −0.044, geometry −0.038, geometry+environment −0.096, so **environment adds nothing and geometry adds almost nothing either**. Diagnosed, not asserted: 61% of variance is between sites, but site-level corr(distance, level) is only −0.26 over 48 sites — an R² ceiling near 0.07 — because aggregating to per-session medians over drive routes inside a 2.4 km AOI averages the distance leverage away, and what actually separates sites (antenna tilt, height, power, sector) is data this project does not have. The incremental R² also **flips sign with the inclusion threshold** (−0.06 at ≥20 measurements, +0.02 at ≥30), which is what noise looks like. The pipeline recovers a planted −20·log10(d) law at R² > 0.8 on synthetic data, so the null is the data's, not a broken script. Consequences that bind: the risk index must not be presented as predicting delivered signal quality; `signal_residuals.csv` is written but deliberately **not served**, because with a geometry model this weak "underperforms its geometry" is mostly unexplained variance; and the fix is a wider AOI, not a better estimator — 5.7 km² leaves no environmental gradient to detect, and no change of model repairs that.

**The AOI was the ceiling, and widening it moved three things at once.** `data/malaysia/` is the same §1 feature table over all 1,164 communication towers OpenStreetMap has in Malaysia, built by `data/prepare_malaysia_dataset.py` from the same four sources as the pilot (Copernicus GLO-30 via Planetary Computer, ASF HAND, OSM, geoBoundaries ADM1). Against the 132-tower Sunway box: HAND median 1.12 m → 3.88 m with a 442 m tail, elevation −0.6 → 2,235 m, and the risk index's IQR 0.091 → 0.361. The compression the Method page attributes to flat low-lying ground **is** flat low-lying ground — it was the AOI, not the model, and nationally the attribution panel stops being one bar: flood-dominant falls from 130/132 to 735/1,164, with `power` (229) and `equipment` (200) leading the rest. Two provenance rules bind. Tower positions are OSM features, not an operator asset register, so per-state counts (Sarawak 232, Selangor 228, Perlis 2) describe **OSM mapping density, not deployment** and must never be rendered as coverage. And 96% of masts carry no radio tag, so `radio` is the literal string `UNKNOWN` rather than NaN — `check_schema` forbids NaN outside `age_years`, and writing UNKNOWN keeps "we do not know" visible in the CSV instead of hidden inside `EQUIP.map(...).fillna(0.5)`. `adapter/ml_source.py` serves this table when it exists and falls back to the pilot one when it does not, so a checkout without `data/malaysia/` still boots. Each record's `territory` is now its ADM1 state rather than the old hardcoded `"Selangor"` — `config/crews.json` already rosters all 16 territories, so the optimizer had nothing to strand: measured, the 117 national maintain-band orders pack into 57 assignments across 11 crews in 10 territories, with the other 60 returned in `unscheduled` as the invariant requires. Two spellings had to be reconciled and neither would have thrown: geoBoundaries writes **Malacca** where crews.json rosters **Melaka**, so `TERRITORY_ALIASES` maps it or every Malaccan tower silently becomes unschedulable; and Kuala Lumpur, Putrajaya and Labuan are **enclaves**, wholly inside another state, so `assign_states` tests the smallest state first — by its *largest* ring, because Selangor's smallest offshore islet otherwise sorts ahead of the whole of KL and takes its 38 towers.

**The flood factor now has ground truth, and it is observed water — never failure.** `data/prepare_flood_labels.py` builds two label sets and `model/flood_eval.py` scores against them with a confusion matrix. Neither label records an outage, a fault or a maintenance action; both record *this ground was observed under water*, from sensors the feature table never touches, which is the difference between ground truth and the withdrawn classifier's restated assumption. (1) **JRC GSW v1.3**, Landsat 1984-2020, 38,948 points over 400 randomly drawn 0.05° land cells: positive = observed under water but not permanent, negative = never once, with permanent water (occurrence ≥ 75%) **excluded from both classes** — a model that scores well by finding rivers has answered a different question. Its weakness is that Malaysian non-permanent water is heavily paddy, aquaculture and ex-mining ponds. (2) **UNOSAT FL20191217MYS**, Sentinel-1, 15 Dec 2019, Johor, 12,000 points inside the analysts' own AnalysisExtent so the negatives mean "looked at, not flooded"; 2.06% positive, and its class field reads literally `Flood Water`. It is never fitted — it is scored once, by parameters chosen on GSW, and it is the control for the confound in (1). Three rules hold the evaluation up. Every split is **GroupKFold on ADM1 state**, because points 5 km apart share a catchment and a random split scores near-duplicates. The operating point reported is **top-10%**, matching `MAINTAIN_QUANTILE`, because crew capacity decides dispatch size, not a probability; accuracy is reported but flagged, since "never flooded" scores 0.98 at a 2% base rate. And **weight tuning stays inside the flood factor** — `equipment` and `power` have no inundation signature, so refitting the AHP weights against a water label would rebuild the exact circularity the classifier died of; the full index is reported unfitted and its dilution measured (event PR-AUC 0.173 for flood alone vs 0.144 for the whole index).

**One change survived that evaluation: a slope gate on flood, and it broke a documented invariant on purpose.** `PARAMS["flood_slope_s0"] = 60.0` multiplies the flood membership by `exp(-slope/60)`. Water has to stand somewhere; HAND says how far above drainage a site sits and nothing about whether the ground could hold water, so the ungated membership scored a valley wall and flat ground at the same HAND identically and charged the wall twice — once as `terrain`, once as `flood`. Measured out-of-fold on GSW and on the held-out 2019 event, every confusion cell improves (event top-10%: TP 136→146, FP 1064→1054, FN 111→101, TN 10689→10699) with PR-AUC ×1.60 nationally and ×1.45 held out, and ROC-AUC unmoved. Four things about how it was chosen matter more than the number. The ablation says the gate is the **whole** effect: log-space HAND moves average precision by 0.0003 and explicit sub-signal weights by 0.0000, so two plausible ideas were dropped rather than shipped alongside it. Re-fitting the existing `hand_h0/hand_k/water_d0` buys nothing (`flood_tuned` ≈ baseline) — this was not reachable by tuning. `60°` is **dominance-selected, not fitted**: fitting on average precision alone runs to 0.15°, i.e. "flat ground only", and 60° is the strongest gate that degrades no metric on either label set. And it **cannot be found on the pilot AOI**, whose slope is 3.5° at the median. The cost is real and stated: slope is no longer monotone in total risk, since flood falls faster than terrain rises at moderate slopes, so `test_monotonic_in_raw_hazard` now excludes slope and `test_slope_raises_terrain_and_lowers_flood` pins the two opposite roles instead. The gate is suppression only — it can withdraw exposure, never invent it — and on flat ground it is exactly inert, both pinned by tests. It reshuffles **45 of the 116 towers in the national maintain band**, which a planner will notice.

**The noisy-OR/AHP index no longer produces the served score — a supervised model does, and it is checkable against a stated ceiling, which the index never was.** `model/maintenance_need.py` (inference) plus `notebooks/maintenance_need.ipynb` (training) replace the physical index as the source of `/towers`' `risk` and `attribution`. `model/risk_index.py` is **not deleted** — `model/flood_eval.py` and `model/validate.py` still import it, and it survives as the baseline row every report compares the model against; a PR-AUC with no baseline is unreadable. The k-means typology that used to live at `model/archetypes.py` — genuinely unsupervised, shipped no route — was deleted outright rather than migrated; nothing in the frontend read it, and its removal is a straight subtraction with no seam left behind.

The reason a supervised model can exist at all here is the same reason the last one had to be withdrawn, worked around rather than ignored. `maintenance_classifier` reported 0.974 out-of-fold AUC by inverting a quantile cut on the same six features it was given — arithmetic scored as prediction. `data/prepare_maintenance_records.py` generates a **synthetic** maintenance-record dataset (no real operator or MCMC history exists for this prototype) under five rules that keep it from repeating that failure, the first of which is mechanical: the generator's imports are parsed by an AST test that fails the build if `risk_index` ever appears in them. Hazard is driven by *observed* measurements — JRC GSW occurrence, sampled EVI, sampled clay and soil moisture, and since generator v2.0 `hand_m` and `slope_deg` as well — through functional forms that are the generator's own (linear ramps, a shape-1.5 HAND decay, an exponential in grid distance), never the index's logistic memberships combined by noisy-OR. A per-site latent — build quality, drainage, genset age, a frailty term — still perturbs the label, attenuated by `LATENT_STRENGTH = 0.15`. The generator's own latent intensity is scored as an **oracle** and reported alongside every other number: on the shipped dataset, `oracle` reaches ROC 0.985 while the served model reaches 0.910 and the retired index 0.678 — a model landing at the oracle would mean the generator leaked, not that the model is good.

**The synthetic register had to be made plausible before it could be believed, and fixing it exposed a calibration bug.** `OBSERVABLE_LOG_SPREAD = 5.5` is a ratio of ~1e14 between the quietest and loudest site, and the Poisson draw honoured all of it: the shipped register had a tower with **2,199 corrective orders in 36 months**, about 60 a month on one mast. The binary label stops caring above lambda ~3 (P(>=1) = 0.95), so that tail bought no discrimination while making `n_corrective_36mo`, `downtime_hours` and `cost_myr` unusable as quantities. `_saturate()` soft-caps a site's monthly rate at `MAX_MONTHLY_RATE = 0.8` via `x -> c(1 - exp(-x/c))`, applied to the row total and shared back proportionally so cause shares — and therefore `dominant_factor` and the attribution panel — are untouched. The shape is load-bearing: **strictly monotone**, so no two sites swap order and `lambda_true` stays the oracle the leak check depends on (oracle ROC 0.982-0.984 across every cap tested); **identity near zero**, so the region where the label is actually decided is unchanged; **asymptotic**, not clipped, because `np.minimum` would flatten the top decile onto one value and destroy the oracle's ranking inside it. Shipped: max 41 tickets, p99 31, none above 50, and accuracy is flat across caps from 0.4 to uncapped. Fixing it surfaced a second bug: **`calibrate()` could not predict the run it was calibrating.** Its docstring claimed the bisection and the recorded simulation share a seed, and they did — but recording consumes extra RNG draws inside the month loop for ticket dates, downtime and cost, so the two walked different Poisson streams and the shipped base rate missed the calibrated one by 1.5 points (0.212 vs 0.228). Ticket detail now draws from its own generator, seeded once from the caller's and drawn unconditionally so both modes consume it identically; the base rate now lands at 0.2113 against a 0.21 target.

**The generator was retuned for accuracy at the project's request, and what that bought and cost are both measurable.** v1.0 planted five mechanisms the noisy-OR index structurally cannot represent — a clay x wetness interaction, a non-monotone mid-EVI vegetation hump, a power-distance threshold cliff, a per-state contractor effect that a random K-fold leaks and `GroupKFold` does not, and a leakage-bait column `n_site_visits_36mo` sitting where a real operator export would put it. All five are **removed**: the hazard curves are now smooth and monotone in their drivers, `planted_traps.json` is no longer written, the bait column is no longer written at all, and the notebook's trap-recovery section is replaced by a split check that verifies random KFold and GroupKFold now *agree* (measured: −0.008 PR-AUC). Three knobs moved with them — `OBSERVABLE_LOG_SPREAD = 5.5` renormalises the summed observable intensity to a fixed log-spread (replacing v1.0's saturating power law), `LATENT_STRENGTH = 0.15` pulls every latent multiplier toward 1, and reporting noise is off. Served model: **ROC 0.581 → 0.910, PR-AUC 0.292 → 0.765, top-10% precision 34.2% → 82.9%**. Without demo-case planting the same pipeline reaches ~0.948/0.835/89.7%; the difference is the planted ceiling, not the model. None of that came from the model — `PARAMS` and `FEATURES` are untouched; the label was made more learnable. What it cost is the argument the traps were carrying: the report can no longer show that the supervised model recovers structure the index cannot, and the oracle ceiling now sits 0.036 ROC above the served model rather than 0.20, so "a perfect model cannot reach 1.0" is a much weaker claim than it was. Two things fixed on the way: `calibrate()`'s bisection floor was `1e-3`, **above** the ~3e-4 scale the new spread needs, so it silently returned its own floor and missed `TARGET_BASE_RATE` (0.29 instead of 0.21) — now `1e-9`; and `SPURIOUS_RATE`, which scatters misfiled tickets uniformly while the new spread concentrates real ones, pushed the base rate to 0.66 before being set to 0. `simulate()` now raises above `MAX_TICKETS` rather than hanging on an uncalibrated scale. **The demo cases had to be rebuilt afterwards, because the retune silently killed all of them and a comparison bug hid it.** They read 5/33 matching their registered `expected_role`, and three faults stacked. (1) SELECTION: `protected_site` drew from `np.argsort(-gsw)[:120]`, but `gsw_occurrence_pct` is 0 for 97.9% of towers, so the sort was ties at zero and "high exposure" meant a random site — two of four came back at lambda 0.000 and 0.298, which cannot be a false positive because nothing ranks them high. Selection is now on the site's own observable intensity. (2) FORCING: `LATENT_STRENGTH = 0.15` made a forced latent inert, and no plausible latent (build quality, drainage: a factor of two) can move a site against a 5.5-sd log-spread anyway. A case now states the rate it should BEHAVE at as a population quantile and the multiplier is solved for — scale-free, so it survives `calibrate()`. The new `demo_multiplier` latent is applied at FULL strength, deliberately outside `LATENT_STRENGTH`, because a demo case is by definition a site whose hidden history is extreme. The Poisson draw still decides, so `expected_role` stays falsifiable. (3) The COMPARISON was wrong independently of any of that: `expected_role` mixed confusion cells with narrative labels (`count_is_not_cost`, `denominator_matters`), which can never equal an observed TP/FP/FN/TN, so 13 rows were guaranteed to read as failures; and `twin_pair` expected one TN and one TP from a pair the model *cannot separate*, which is impossible rather than strict — a pair with near-identical scores can only land {TN,FN} or {FP,TP}. Cases now carry `expectation_kind` (confusion | pair | narrative) and the notebook checks each by its own rule. Result: **7/8 confusion cases and 6/6 twin pairs**. One more selection fix was needed after the first pass read 1/4 on `protected_site`: the case claims the model DISPATCHES the site, so it must clear the top-10% cut, and drawing from the top 13% by observable intensity was not tight enough — three of four sat at risk 0.19-0.68 against a cut near 0.7, correctly ticket-free but never dispatched, so true negatives rather than the false positives the case exists to show. Drawn from the top 5% it reads 3/4. The cost is real and is the point: planting drops the headline from ROC 0.948/PR 0.835 to **0.912/0.785**, because 33 sites (2.8%) are now genuinely unlearnable. Softening the targets does not recover it (p25/p92 and p30/p88 both score the same or worse) — the cost is having label-contradicting sites at all, not how extreme they are, so the only dial is how many to plant.

**`lightning`, `equipment` and both JRC GSW columns are absent from the served attribution, each for a measured reason rather than a judgement call.** `flash_density` is null for all 1,164 national rows, and the adapter dropped lightning before this model existed. `equipment` was dropped later and deliberately: its sole feature `radio` is `UNKNOWN` for 1,119 of 1,164 rows (96.1%; the rest are 29 NR, 15 LTE, 1 GSM), and the trained booster split on it **0 times across 91 trees**, gain 0.0000 — so `factor_shares()`, which sums |SHAP| per group, returned exactly 0.000 for every tower and no tower could ever be equipment-dominant. Dropping it moved the served model from ROC 0.949/PR 0.846 to **0.951/0.849** — measured at that point, before the demo-case and ticket-cap work below moved the headline again: a dead column, removed. The mechanism is real and the data is missing — restoring it needs an operator asset register (air-interface, install date, power rating), the same shape of gap as lightning's missing climatology. `model/risk_index.py`, `scheduler/urgency.py` and the Weights sliders keep their own equipment factor; they are the index path, not the model path, and `urgency_days` reads shares with `.get(factor, 0.0)` so a missing key contributes 0 rather than raising. `gsw_occurrence_pct` and `gsw_recurrence_pct` went last, and the diagnosis is a **sampling** fault, not a dataset fault: `data/prepare_land_features.py::gsw_reduction` samples at the tower point with `buffer_m=0`, and a mast is never built inside a water body, so 1,140 of 1,164 towers read 0. Of the 24 that do not, 5 needed corrective work — 20.8% against a 21.0% base rate, **lift 0.99x**, which is zero information rather than weak information. In the model it was worse than weak: `min_data_in_leaf = 25` makes a split isolating 24 rows illegal, and 24 is the largest group above zero, so no split was ever legal; training with and without the two columns gave **identical metrics to four decimals**. Buffered sampling was measured before dropping — JRC GSW v1.3 re-fetched at 30 m from Planetary Computer (anonymous, no Earth Engine) over 94 tiles — and it works: at 100 m, 127 towers carry water history at lift 1.45x and the model splits on it, PR-AUC 0.8493 → 0.8535. It was dropped anyway, because +0.004-0.007 PR-AUC did not justify moving one column onto a second fetch route. The caveat that would matter on revisiting: the synthetic label's own flood term reads the POINT value, so this test understates what buffered GSW is worth, and the experiment should be re-run against real work orders rather than assumed settled. Served model is **12 features, 4 factors**; `land_cover` in the same file already samples over `LAND_COVER_BUFFER_M = 100` for exactly this reason, so the argument for buffering was in the file, just not applied to this reducer. `vegetation` is new — EVI and land cover became per-tower features rather than only map tiles — and needed its own `config/actions.yaml` entry (`vegetation_clearance`, civil crew) before a vegetation-dominant tower could produce a work order instead of a `KeyError`.

**Two more layers sit beside that model; one enters the dispatch ordering, and the SHAPE of how it enters mattered more than which layer it was.** `model/novelty.py` carries `novelty_scores` (Isolation Forest over the 11 non-categorical model features) and `condition_scores` (a one-sided read of the 30-day telemetry block); `model/profiler.py` carries eight declarative rules. `model/ensemble.py::blend_priority` rank-blends `condition` into `risk` at `CONDITION_BLEND_WEIGHT = 0.25`, and the decision bands are cut on that blended `priority`. **`risk` itself is never touched** — it stays the model's calibrated probability and the quantity the report's oracle check compares. `novelty` and `flags` enter nothing and ride the record as description.

**Satellite change and the observation ledger (v2.3, 2026-09-12).** `data/prepare_land_change.py` reuses the Sentinel-2 EVI sampler over two 365-day windows, 730 days apart: 2025-09-12→2026-09-12 and 2023-09-13→2024-09-12. The generator now joins that CSV and deliberately charges regrowth: this is **grading our own synthetic generator**, not evidence of real maintenance benefit. The three-rank implementation renormalises available weights per tower and preserves the exact two-rank path when change is absent or disabled; `risk`, urgency and `/score` are unchanged. Two YAML-thresholded profiler rules describe high-priority/quiet-ground and low-priority/active-ground disagreements; neither reads maintenance history. `model/feedback.py` appends raw windows and comparisons once per cache construction, protected against concurrent first requests. Retraining remains manual. Ledger absence is null, malformed lines are counted, and all page counts come from the gitignored ledger — no health fixture.

**The gate was the limit, not the cap and not the data.** Three combination shapes were measured. A gate on `novelty` shipped first and died on the comparison that should have been run first — anything dispatching more towers must be scored against a *cut* dispatching the same number, never against the untouched top-10% — at F1 0.5751 against 0.5855. A gate on `condition` looked better and is, on held-out seeds under a realistic telemetry-noise model, **negative**: −0.0125 F1, ahead in 1 of 5. Raising its cap from 5% to 20% changed nothing, because the cap was never what bound it: **a gate touches the second opinion at one threshold and reorders nothing**, discarding what condition says about every other tower. The rank blend uses it everywhere. Held-out seeds 5-9, matched budget, GroupKFold on ADM1 state: lightgbm alone F1 0.6623 / 138.4 TP; gate p85 cap5% 0.6497 / 135.8 (−0.0125, 1/5); gate p70 cap20% watch+ok 0.6738 / 140.8 (+0.0115, 5/5); **rank blend w=0.25 0.6814 / 142.4 (+0.0191, 5/5)**. Standalone the two rankers are complementary — model ROC 0.905, condition 0.884, a 50/50 rank blend **0.929**, above both. On the shipped seed the blend reads ΔF1 **+0.0606**, 107 TP against 96, with 25 towers swapped into the dispatch list of which 21 needed work. Weight is swept on seeds 0-4 (0.2 and 0.3 both win 5/5, 0.5 wins 2/5) and set to the **midpoint rather than the argmax**, then verified on 5-9; past ~0.4 the ordering is worse than LightGBM alone. A tower with no telemetry keeps its bare model rank rather than being pushed down — missing telemetry is not evidence of a healthy site, and a fleet part-way through a monitoring rollout must not de-prioritise its unmonitored towers. **An earlier note in this file said "blending is worse at every weight"; that was measured on `novelty`, was true of `novelty`, and was carried over to `condition` without being re-run. It was wrong there, and the gate it justified cost real accuracy.**

**Which signal may enter, and the necessary condition that decides it.** `novelty` may not. An isolation forest scores |deviation from typical| and maintenance need is **monotone** — a site with unusually *few* alarms is exactly as anomalous as one with unusually many — so a two-sided statistic aimed at a one-sided target cancels most of the signal: given a telemetry block ranking the label at ROC 0.93, the forest returns **0.45-0.52** inside the band that decides dispatch while a one-sided read of the identical column returns **0.80-0.83**, against the model's 0.65-0.74. **`detector_auc > model_auc` inside the eligible band is the necessary condition for any second opinion to be worth acting on**, it is reported in `maintenance_need_report.json` under `second_opinion.detectors_in_escalation_band`, and it is the check to re-run before trusting any future layer. Abstention stays rejected on its own evidence: calibration error is flat across novelty quintiles (0.008/0.039/0.012/0.006/0.015) and so is ROC (0.85-0.91) while the base rate climbs 0.061 → 0.424, so novelty tracks risk rather than model error and dropping the strangest 30% makes ROC and PR *worse*.

**What gives Layer 2 anything to say is an information advantage, and it took ten failed dataset configurations to find it.** `data/prepare_maintenance_records.py` v2.2 writes `site_telemetry.csv` — rectifier alarms, battery sag events, door-open hours over 30 days, derived from the site's own hazard intensity plus gaussian noise. It ranks the label at **ROC 0.957 on its own** and `model/maintenance_need.py`'s `FEATURES` deliberately excludes it: the counters cover 30 days and the label covers 36 months, so this dataset holds **no aligned (telemetry, outcome) pair to fit**. A supervised model cannot use it; an unsupervised score needs no labels and can read it the day it starts flowing. That asymmetry is the textbook reason an unsupervised member earns a place in an ensemble and the only reason measured here that works. `data/test_maintenance_records.py` fails the build if telemetry ever leaks into `FEATURES`, because the moment it does the supervised model regains the advantage and the ensemble's whole case evaporates.

**The estimator, not the dataset, was the blocker — and that is worth more than the result.** An earlier gate on `novelty` shipped and was removed by the comparison that should have been run first: anything dispatching more towers must be scored against a **cut** dispatching the same number, not against the untouched top-10%. On that comparison the forest gate lost at every budget from 92 to 162 (F1 0.5751 against 0.5855 at 140 dispatches, 118 of 140 towers identical either way). Ten hazard-planting configurations were then measured — Mahalanobis rare-configuration boost 2/4/10 × pocket 117/59/35/18, plus a region-concentrated variant and a label-under-reporting variant — and **every one landed inside the no-planting band**; the strongest boost even *raised* LightGBM's PR-AUC (0.765 → 0.775), because the supervised model sees the same columns plus the label. Planting harder always helps the tree more. The actual diagnosis came from measuring the necessary condition directly: given the same 0.93-ROC telemetry block, an isolation forest returns **in-band AUC 0.517** while a one-sided read of the identical column returns **0.825**, against the model's 0.737. A forest scores |deviation from typical| and maintenance need is **monotone** — a site with unusually *few* alarms is exactly as anomalous as one with unusually many — so a two-sided statistic aimed at a one-sided target cancels most of the signal. **`detector_auc > model_auc` inside the eligible band is the necessary condition for any gate to beat a lower cut**, it is reported in `maintenance_need_report.json` under `second_opinion.detectors_in_escalation_band`, and it is the check to re-run before trusting any future layer. Two framings stay rejected: blending into `risk` (PR-AUC 0.7708 → 0.7539 at the lightest weight, monotone down), and abstention — calibration error is flat across novelty quintiles (0.008/0.039/0.012/0.006/0.015) and so is ROC (0.85–0.91) while the base rate climbs 0.061 → 0.424, so novelty tracks risk rather than model error and dropping the strangest 30% makes ROC and PR *worse*. Two limits are measured and stated rather than buried. The advantage is a function of **telemetry quality**: it shrinks as noise rises and the shipped generator's model is optimistic — it draws i.i.d. noise per window, whereas real counters carry a **persistent per-site bias** (calibration, vendor, reporting practice) that no amount of history averages away. Under a bias-split model (0.35 persistent + 0.357 measurement, same total) the 30-day block falls from ROC 0.957 to 0.894 and the ensemble's edge shrinks accordingly; every held-out figure quoted above already uses that harsher model, so it is the conservative number. And the advantage exists **only while the gap exists**: give Layer 1 a 36-month telemetry aggregate and it reaches ROC 0.9598 / PR-AUC 0.8652 / F1 0.7268 against today's 0.9112 / 0.7704 / 0.6705 — **+0.0563 F1 and +12 TP, roughly six times what the ensemble buys** — and the ensemble then loses to it by −0.0477 F1. The leak check stays clear at that point (PR gap to oracle +0.0853), so that is a real improvement and not the telemetry collapsing onto `lambda_true`. **The ensemble is a workaround for a data-plumbing gap; closing the gap is worth far more than the workaround.** Doing so needs a `FACTOR_GROUPS` entry and a `config/actions.yaml` key so a telemetry-dominant tower can raise a work order, which is the real cost, and the blend should come out when it lands. `RARE_CONFIG_BOOST` stays inert at 1.0 with its ten-row sweep recorded, for the same reason `SPURIOUS_RATE` and `DROP_RATE` sit at 0.0: the next person to have that idea should read the numbers rather than re-run them.

**Layer 3's rules are thinner than they look, and half of the ones worth wanting cannot exist.** Three natural rules were dead before the file was written — `age_years`, `exposed_pop` and `flash_density` are null for all 1,164 rows, the same shape of gap as `lightning` and `equipment`. Of the six that survive, the two loudest report that *no crew can reach the site* — `unassigned_territory` (4 towers) and `out_of_crew_range` (318). Each rule once carried a numeric `weight` feeding the escalation score, and those two were pinned at 0.0 after an integration run showed 318 towers saturating the escalation cap on their own; the weights are gone entirely now that the gate is, rather than lingering as a field nothing reads — the same reason `_three_band_decision` lost its always-empty override argument. And **no rule may read maintenance history**, which is the constraint that shapes the whole layer: `sum(n_corrective_36mo >= 1)` = 246 and `sum(needed_corrective_maintenance)` = 246 — the same 246 rows, because the label *is* that column thresholded. A repeat-visit rule is the most natural rule to want here and it would predict the target by construction, reporting arithmetic as accuracy exactly as `maintenance_classifier` did. `model/test_second_opinion.py::test_profiler_never_reads_maintenance_history` parses the module's AST — not a grep, since the docstring names those columns on purpose to explain the ban — and excludes docstring nodes while checking `Name`, `Attribute` and string `Constant`, because `df["n_corrective_36mo"]` hides the name in a constant. The honest home for history is `maintenance_panel.csv`, whose recency columns are computed strictly before each row's reference date. Rule *predicates* stay in Python and only thresholds, labels and the two switches (`enabled`, `evaluable`) live in YAML — a rules DSL would be a second language to debug, and `policy.yaml` already sets the precedent that config carries parameters, not logic.

`/towers` and `/score` can now legitimately disagree. `/score` re-scores under caller-supplied AHP weight overrides — a feature with no equivalent for a model that has no per-factor weight to override — so it stays on the index unconditionally while `/towers` serves the model. That is a stated product inconsistency, not an oversight: reconciling what the Weights sliders mean once the baseline score is learned rather than asserted needs a decision this file does not make unilaterally. `/stability`'s 500 perturbed-weight draws have the same problem and the same non-fix: under the model, `_compute_stability_draws` returns `None` rather than perturbing weights that do not exist, and `risk_lo`/`risk_hi` collapse to `risk` itself. `None`, not a zeroed struct — the frontend's existing `Stability | null` contract (see `useStabilityQuery` below) was already built to receive exactly this.

**The blend has to reach the scheduler, or the two halves of the pipeline disagree about the same tower.** The decision bands are cut on `priority`, so a site can be in the maintain band because its live counters are hot rather than because its standing risk is high — and for one release `scheduler/optimize.py::priority()` still read `risk`, which let exactly that tower enter the dispatch list and then sort to the bottom of it. It now reads the served `priority` and falls back to `risk` for any record without one (the mock fixture, and any caller on the §1 minimum contract), which fixes the sort key, the `risk_weighted_wait` accumulator and `override.py`'s re-scoring in one place because all three already went through that function. One consequence is stated rather than hidden: `risk` is a probability (p50 ~0.12 under the served model) and `priority` is a percentile rank (p50 0.5), so the ABSOLUTE `risk_weighted_wait` roughly quadruples across that boundary. The reported headline is `risk_weighted_wait_reduction_pct`, a ratio between greedy and nearest-first running through the same Optimizer and differing only in `sort_key_fn`, so the claim it makes is unaffected — but the absolute figure is not comparable across releases. `scheduler/explain.py` gained the matching reason line: a tower in the run on telemetry rather than on standing risk says so, because otherwise a planner sees a low-risk site dispatched ahead of higher-risk ones with nothing explaining it. `scheduler/test_ordering.py` pins both.

**What the ensemble deliberately does NOT reach, each for a reason.** `urgency_days` is untouched: shortening a deadline because counters are hot would double-count, since the blend has already moved that tower into dispatch, and urgency is mechanism-weighted by attribution share while telemetry belongs to no factor. Coupling it would need a `coupled_factors`-style policy entry and a decision about strength, which is a config question and not this file's to answer unilaterally. `/score` still serves the noisy-OR index under caller-supplied AHP weights — a blend has no per-factor weight to override — so the documented `/towers` vs `/score` divergence is unchanged and not widened. `/stability` still returns `None` under the model. `agent/` is untouched: it reports tool output verbatim and the optimizer still decides. And the work order's `why` string still carries attribution only; the profiler's flags ride the record where the UI already renders them, and duplicating them into crew-brief prose would put the same sentence in two places that then drift.

**`GET /model/health` exists because the training report was read by nothing, and the UI's numbers were hand-typed.** `maintenance_need_report.json` sat on disk with no endpoint while `MethodPage.tsx` carried the scorer table as literals — `roc: '0.910', tp: 97, fp: 20` — which had already drifted from the artifact by the time the route was written. A number that must be re-typed after every retrain will be wrong after some retrain, so `api/routes/model.py` serves the file and both `/health` and the Method page read it; neither can now disagree with the notebook or with each other. The response separates training and serving on purpose: `report` describes a **training run**, `serving` describes **this process** — band counts, escalations, how many towers carry no telemetry, and `source: model | index`. They can legitimately disagree, and a checkout with no trained artifact serving the physical index against a report describing the model is exactly when you need to be told which you are looking at. `report` is `null` on such a checkout, and a corrupt artifact returns `null` rather than a 500 — the same "configuration state, not an error" contract `load_booster()` keeps. The page has **no offline fixture**: every figure on it is a measurement, and fabricating a confusion matrix on the one screen whose job is telling you whether to trust the model would be the worst place in the app to invent a number, so `useModelHealthQuery` falls back to `null` and the page says so. Panel order is load-bearing — provenance first (every figure is against synthetic labels), guardrails second, numbers third: a reader who meets the confusion matrix first will believe it before reaching the caveat. The guardrail panel is the part that makes this *health* rather than *metrics* — leak check, split inflation, beats-index, the `detector_auc > model_auc` necessary condition, the forest being excluded from the ordering, matched-budget verdict, base-rate range, demo cases — each row testing something that has failed silently at least once, and each one stating a word as well as a hue so it survives a colour-blind reader.

Key invariant: **scored-tower record** (`tower_id`, `risk`, `decision`, `dominant_factor`, `urgency_days`, `attribution`, documented in `docs/Backend_Handoff.md` §1) = contract boundary between risk index and scheduler. Scheduler consumes it, never recomputes scoring.

Route registration order in `api/main.py` matters: `baseline` registered before `schedule`, else `/schedule/baseline` shadowed by `schedule.router`'s `/schedule/{run_id}`.

API response shapes frozen (frontend built against them ahead of backend completion) — when changing backend endpoint shape, `api/schemas.py` and `src/frontend/src/api/types.ts` must update together.

**Live-vs-offline data flow.** Every query goes through `withOfflineFallback()` in `api/queries.ts`: on network failure returns matching `fixtures/` data *and* sets global `useOffline` flag, which renders `OfflineBanner`. Rule that makes this safe: fallback never silent — demo narrated as live while quietly showing fixtures worse than visible failure.

**Fallback must be real data or `null` — never zeroed struct.** `withOfflineFallback` takes whatever you hand it, and zeroed object is truthy, so every consumer's `data ? … : '—'` and `data ?? BASELINE` guard silently takes wrong branch. This shipped: `useStabilityQuery` fell back to `{rho_mean: 0, …}`, so offline status chip rendered `ρ 0.00` and `/weights` rendered `Draws 0` as though measurements — and ρ = 0 means "ranking is pure noise", most alarming reading model can produce, shown in calm grey. `TOWERS` and `CREWS` legitimate fallbacks because real fixture exists; no fixture stability run exists, so honest fallback is absence. Type query `T | null` so compiler enforces guards. `useLiveTowers(weights)` sits on top, single source of truth for "towers as scored by current slider weights"; map and every console module read from it so they recolour together. At baseline weights it passes `/towers` through; off-baseline it debounces ~300ms and calls `POST /score` (server authoritative), falling back to client-side `lib/scorer.ts` noisy-OR only when genuinely offline.

**Design system has one governing rule: cool accent = interface chrome; warm colour is data, never control chrome.** `--color-accent` (violet `#7c3aed`) carries nav, focus, controls, and interactive states. `--color-maintain`/`--color-watch`/`--color-ok` and `--color-alert` are reserved for tower risk; other map data may use warm hues only with a numeric legend and explicit quantity, as the HAND depth bins do. Tokens live in `@theme` in `src/index.css`. Accent *value* changed twice (cyan -> violet -> darkened violet for light theme) but *role* never does; warm hue on control = bug, not the token. `.spine` = band-coloured edge applied to any surface carrying tower severity via `--spine` custom property.

**Amendment (2026-09-02, schedule tab): crew capability is a third colour dimension.** Rule above originally allowed colour to carry chrome and severity only, so `lib/roleTeams.ts` refused a hue and left the four capabilities to grouping, label and glyph. Failed in practice: glyph is 14px grey stroke, label 12px, so Civil/Power/RF/Electrical rendered as four identical stripes on a 900px board and the role grouping — whole point of the role-grouped timeline — was invisible. Crew type now carries hue from `lib/roleColors.ts`, same two-ramp construction as `lib/colors.ts` (`ROLE_COLORS` fill >=3:1, `ROLE_INK` text >=4.5:1, both measured against `#ffffff` and `#f2f5fa`). Ramp is deliberately **cool** (indigo/sky/cyan/slate) — not because old prohibition survives, it does not, but because a job bar carries role AND severity on the same element and a warm role would collide with the severity reading on one mark. **Warm is still severity, and warm on a control is still a bug.** Reserve is still neither: `lib/reserveHatch.ts` unchanged, per the readiness rule below. `tintedChip()` in `roleColors.ts` is shared recipe for the `ink` text / `hue66` border / `hue1a` wash construction `SelectionHud`'s band chip established — four hand-typed copies of `${hue}66` is how the band triad drifted across the map layer before.

**App is light-themed, severity has two ramps, not interchangeable.** `lib/colors.ts` exports `bandColor()` for FILLS (map circles, bars, spines, chip backgrounds; >=3:1) and `bandInk()` for TEXT and thin marks (>=4.5:1); Tailwind equivalents `bg-watch` vs `text-watch-ink`. Dark theme needed one ramp because saturated hue on near-black clears both bars at once — on white it does not, and old `#ffb244` measures 1.90:1 as text. **`bandColor()` driving a `color:` property is a bug.**

**`--color-overlay` is hinge whole theme turns on.** Every surface tint and hairline in component tree written as `overlay/<alpha>` (175 usages) not literal, so ink/paper polarity of entire app is one token. It is `#0d1526` here; setting it to `#ffffff`, alongside ground and text ramps in `@theme`, is most of what returning to dark theme takes. Do not reintroduce `white/<alpha>` utilities — they hardcode polarity back into 38 files.

**Type is two families and eight named steps; there are no ad-hoc pixel sizes.** `--font-display` and `--font-sans` are deliberately the *same* face (Fira Sans) — the previous Space Grotesk/IBM Plex split was honoured at only 9 of 29 headings, and a split that is wrong two thirds of the time is not a system. Hierarchy is carried by **weight and size**, which cannot drift the same way. The scale lives in `@theme` as `--text-eyebrow|micro|ui|body|lead|title|display|hero` (10/11/12/13/15/20/32/40px, each with its own line-height), and replaced 14 arbitrary values across ~137 call sites. **Do not reintroduce `text-[13px]`-style arbitrary sizes** — if a role is genuinely missing, add a step to the scale. **The rule is currently being violated**: ~37 arbitrary sizes have crept back, concentrated in the newer map HUD (`FloodPanel`, `OpacityModule`, `SearchModule`, `SelectionHud` — mostly `text-[10.5px]`, a step that does not exist). Do not add more, and prefer collapsing them to `--text-eyebrow`/`--text-micro` when touching those files. `.h-title` in `@layer components` is the canonical heading recipe (family + 600 + tracking), so a heading is one class rather than four utilities a component can get three-quarters right.

**Fira Code's ligatures are switched off wherever it renders, and must stay off.** Fira Code is a *programming* face: unguarded, the interval `0.96 -> 0.99` renders its arrow as a single glyph and `!=` becomes one mark, so a risk readout can be silently restyled into something the user cannot copy back out. `.tnum` and an unlayered `.font-mono, code, pre, kbd, samp` rule both set `font-variant-ligatures: none` plus `"calt" 0, "liga" 0`. No Tailwind utility sets `font-feature-settings`, so the unlayered rule has no utility to outrank — it is a family default, not an override, and is the one exception to the `@layer components` discipline above that is safe by construction.

**Elevation carried by shadow, not glow.** `--shadow-1/2/3` in `:root` = only elevation steps; every glow dark theme used (spine bleed, slider thumb ring, route-depot halo, selected-dot halo) removed, because glow on light ground reads as rendering artefact. `.spine` compensates with 3px rule instead of old 2px-plus-glow.

**Contrast on map console is measured, not assumed — polarity is opposite of what it was.** Basemap is Positron (now served by OpenFreeMap, see below) under **white** wash at **0.20**, so worst case for console dark text is basemap's DARKEST patch (own label ink), not brightest as on Dark Matter. Measured against current composite that worst case gives 3.09:1. Any new text over basemap must clear 3:1 against that composite. Graticule labels and bottom-left readout use `--color-fg`, heavier than secondary readout normally takes: deliberate, and it buys wash down from 0.35 to 0.20. At 0.35 white wash collapsed land/water boundary, and on map of peninsula coastline is most of the information. `text-shadow` (light halo now, not dark) improves legibility but does not change measured ratio. Failing candidates named in comments at each site.

**Component classes in `index.css` must stay inside `@layer components`.** Unlayered CSS beats *every* layered Tailwind utility regardless of specificity, so unlayered `.glass { border: 1px }` silently defeats `border-x-0` on element, and unlayered `position: relative` defeats `absolute`. Both already shipped as bugs here — (since removed) map `Legend` pushed out of map and down over stat tiles, and border-side resets on page headers ignored. These classes are *defaults*; utility on element must always win. Pseudo-element rules (`.spine::after`, `.glass-sheen::before`) carry no utility conflict, stay unlayered.

**Basemap is OpenFreeMap's Positron, and it is vector.** CARTO's keyless endpoint stamps "API KEY REQUIRED" across every labelled tile (verified with `X-Cache: MISS`, since probe off warm edge cache comes back clean — easy way to misdiagnose it). OpenFreeMap serves same open Positron cartography, precisely why chosen over Esri Light Gray or anything else: every contrast figure here measured against Positron, different cartography would void all of them. Re-measured after swap anyway — `--color-fg` on composite's darkest patch is **3.09:1**, still clearing 3:1 bar but tighter than CARTO's 4.43:1, because OpenFreeMap renders label ink slightly darker. Treat that as margin to protect: anything darkening basemap further needs re-measuring, not assuming. Both instances read `BASEMAP_STYLE_URL` from `components/map/basemap.ts` — config used to be duplicated inline in `MapView` and `RouteMap`, so one could drift from other. Vector also changed layer ordering for better: `groundAnchor(map)` finds style's first symbol layer, and every ground overlay (relief, inundation, flood hex, water volume, Earth Engine rasters) inserted **before** it so place names stay legible through water. Towers are not ground, stay on top. Anchor resolved at runtime not hardcoded to `waterway_line_label`, because style is third-party and can be renumbered; missing anchor yields `undefined`, which MapLibre reads as "append on top" — layer still draws. Caveat: OpenFreeMap donation-funded, no SLA, fine here, worth revisiting before production.

**Map console (`/`) is full-bleed and owns whole frame.** `Overview.tsx` composes `MapView` plus floating modules from `components/hud/`; no chrome is layout parent of map, so map never resized by panel appearing. Three things easy to break:

- **Pointer events.** Overlay wrapper is `pointer-events-none`, each module opts back in with `pointer-events-auto`. Without that discipline invisible positioning boxes around floating modules swallow clicks meant for towers underneath. Everything in `MapOverlays.tsx` (dim, graticule, vignette, ticks, readout) stays non-interactive.
- **Stacking.** HUD overlays are later siblings carrying `z-10`/`z-20`, so MapLibre's own control corners pinned to `z-index: 30` in `index.css` or dim and vignette paint over zoom buttons. Zoom control lives bottom-right, not MapLibre default top-right, because status chips occupy that corner.
- **Blur budget: 8 surfaces, ceiling `blur(14px) saturate(1.1)` (`--glass-blur`).** Never blur element that animates position or opacity, never over moving map at full strength. Vignette in `MapOverlays.tsx` is load-bearing, not decoration — does contrast work `backdrop-filter` would otherwise have to, and now fades toward page ground not black, so map dissolves into app instead of into hole. Every glass surface also carries opaque-ish gradient so it degrades acceptably when `backdrop-filter` unsupported, and `prefers-reduced-transparency` swaps them solid.

**`useMapInstance` is how chrome reads the map.** Edge coordinate ticks, cursor readout and scale rule derive from `map.getBounds()`, published from `move` handler coalesced through `requestAnimationFrame` (`moveend` alone makes ticks visibly lag a pan). `window.__map` stays devtools escape hatch only — product surfaces get store, which has real subscription and teardown. `lib/graticule.ts` holds pure tick/scale maths; graticule lines drawn from same bounds as labels, because fixed-pitch grid under real coordinate labels is readout that lies.

**`useMapInstance` is singleton, and there is now more than one map.** `RouteMap` on `/schedule` is second MapLibre instance, deliberately never calls `setMap`/`setView` — if it did, console ticks, cursor readout and scale rule would describe a 200px side panel instead of map they label. Any future embedded map must stay silent same way; only full-bleed console publishes.

**Navigation is single pill; no rail.** `PageHeader` in `components/ui/Panel.tsx` *is* console bar — top row renders `BrandMark` / `NavPill` / `StatusChips` at same screen positions map console floats them at, so nav does not move as you navigate. Editing `PageHeader` therefore changes navigation on every non-map route at once. Overview does not use `PageHeader`; positions same three components itself.

**Shell owns viewport height.** `App.tsx` is only place `h-screen` appears; pages use `h-full` and let flex chain size them. Pages used to declare own `h-screen`, which added `OfflineBanner` height on top of full viewport and pushed bottom of every screen out of view whenever offline mode kicked in.

**AOI scoring uses the current map viewport, not a drawing subsystem.** `AoiModule` snapshots MapLibre's live bounds and sends them with the current weights to `POST /score`; the backend validates the bbox, filters the real feature table, then recomputes risk and band edges for that subset. Polygon/circle/upload placeholders were deleted rather than backed by fake geometry. The model-vintage scrubber remains inert because no vintage field or endpoint exists; it keeps `aria-disabled` so keyboard users can still reach its explanation.

**Live flood dependencies are optional, and the existing MapLibre path renders them.** `flood/` (backend) mints Earth Engine XYZ templates and resolves public WMS templates; `components/map/eeLayer.ts` + `EeLayers.tsx` mount both as ordinary `type: 'raster'` sources, same shape as basemap and terrain tiles. No projection or graticule change needed. `earthengine-api`/`hydrafloods` stay in `requirements-flood.txt`, imports are deferred until an EE tile is requested, and `FloodUnavailable` carries setup steps rather than a traceback. **Layer that cannot be drawn must say so, never render empty**: map ids expire in about an hour (hence refetch), and Earth Engine tile URLs are not necessarily fetchable without credentials, so backend fetches one tile itself and reports `tile_access` — `requires_auth` means frontend deliberately does *not* add the layer. And **date is not imagery date**: each selectable sensor uses a fixed backward window, and every response carries its regional scene count and window. A source-empty regional window errors; within a valid window, gray land explicitly means no usable local observation, so it cannot be mistaken for no flood. Sensor is part of both backend and frontend cache keys. Config: `GEE_PROJECT` plus either `GEE_SERVICE_ACCOUNT_EMAIL` + `GEE_PRIVATE_KEY_FILE` (headless) or `earthengine authenticate` (laptop only). `fixtures/floodLayers.ts` mirrors backend `CATALOGUE` and must change with it; its `earth_engine: null` means "we could not ask", rendered differently from real `configured: false`. **One catalogue breaks that reading and had to be special-cased:** `/backhaul` returns `earth_engine: null` *online*, because it never touches Earth Engine at all, so `LayerPanel`'s footer would otherwise print "Backend unreachable — satellite layers are unavailable" permanently on a tab whose layer is neither satellite imagery nor served through the EE session. The Network tab is exempted ahead of that branch; its real dependency is ITU's GeoServer and a failure there arrives as the per-layer 503 the row already renders.

**`flood_extent` subtracts three things, two are corrections, not taste.** Every selected sensor's water mask loses JRC permanent water and open sea via SRTM's land coverage. Boundary misregistration between static JRC and an observation traces false outlines along coastlines and riverbanks, so `PERMANENT_WATER_DILATION_PX` absorbs two pixels. Sentinel-1 uses median VV backscatter and can confuse smooth dry surfaces with water; Sentinel-2 and Landsat use cloud-masked median MNDWI screening. The optical choices are explicitly not a calibrated fusion product and can miss water below cloud or confuse dark surfaces.

**Tile-access probe is easy to make lie.** Answers "can browser fetch this", and two local faults made it answer "unknown" for reasons unrelated to access: python.org macOS builds ship without usable CA bundle (`CERTIFICATE_VERIFY_FAILED`), and original z7 probe tile made Earth Engine run whole algorithm across peninsular Malaysia and time out. Now uses certifi-backed SSL context and z11 tile over AOI — 1.7 s instead of >30 s, and what browser actually requests. Verified against live project: Earth Engine tiles come back **200 image/png with no credentials**, so `tile_access` is `public` and frontend draws them directly; no tile proxy needed.

**Rainfall is GSMaP, and the unit differs from IMERG.** Measured over Klang Valley, GSMaP's latest image is ~17 h old against IMERG's ~27.5 h; rainfall is the leading indicator (flood extent is what already happened), so those hours matter here more than on other layers. GSMaP is **hourly**, so summing mm/hr over a day gives millimetres directly — IMERG was half-hourly and needed the sum halved. Carrying that 0.5 across would report half the real rainfall while looking entirely plausible. Band is `hourlyPrecipRateGC` (gauge-calibrated, confirmed populated in NRT rather than lagging). Ramp tops at 200 mm, measured not guessed: the 18 Dec 2021 storm peaked at 202 mm/24 h here, and the old 100 mm ceiling saturated across the whole upper half of a real event. **Rain and flood peak on different dates** — the storm fell 17-18 Dec while the water shown on the 20th was already standing, so a user toggling both on one date sees a mismatch that is real hydrology, not a bug. The layer description says so.

**Forecasts are source-selected latest runs, not a scheduler.** NOAA GFS supplies the next 24 h rainfall driver from the newest run carrying all four 6-hour boundaries; CEMS GloFAS `sumAL41EGE` supplies the ASEAN-wide days 1–3 river-discharge return-period outlook through its public WMS. The backend pins the WMS `TIME` and returns issued/valid/source-age metadata; the frontend polls every five minutes. This is intentionally a river-basin warning layer, not local flash-flood extent or depth, and a transparent current layer does not prove no flood risk — blank is GloFAS's normal state, since it alerts only above a 2-year return period. **Both GloFAS layers and GFS rainfall carry `ASEAN_BBOX`, not `MALAYSIA_BBOX`, and the reason is a rendering fault rather than a preference: a raster source's `bounds` culls tile REQUESTS and does not clip pixels, so a box narrower than the source's real coverage does not hide the surplus — it draws it at low zoom, where one tile straddles the edge and the server paints that tile whole, then drops it once the tile stops touching the box. Measured on the outlook layer: a Myanmar alert at 20.6N 97.4E rendered through zoom 4 and vanished at zoom 5, which reads as a broken layer. Either a box covers its source or it lies about it. The two Sentinel-1 diagnostics (`surface_water`, `s1_backscatter`) keep `MALAYSIA_BBOX` deliberately — they run a per-scene radar screen, so area is Earth Engine compute, and their box does match what they build.** When summing an Earth Engine collection, use `_sum_at_source_projection`: bare `ImageCollection.sum()` falls back to a synthetic 1-degree projection, making 0.25-degree GFS and 0.1-degree GSMaP look four to ten times coarser than their source.

**DSWFP is batch pipeline, not request-time layer.** HYDRAFloods' Daily Surface Water Fusion Process (`data/prepare_dswfp.py`) is three chained `ee.batch.Export` tasks — samples → harmonics → one image per day — each writing Earth Engine asset next consumes. They return `None`, take 30 minutes to *days*, nothing displayable until they finish, so this is producer like `prepare_flood_surface.py`, never a route. `build_daily_water` in `flood/layers.py` only *reads* finished asset: HYDRAFloods builds daily image inline inside `export_daily_surface_water` and exposes no public function returning it, so nothing to evaluate lazily and date never exported simply has no image. Four traps, all verified hard way: published Getting Started page **stale against installed code** (`harmonic_coefs` is really `harmonic_image`, `output_confidence` is really `include_confidence`, and `output_asset_path` is required positional in stages 1–2, so page's `None` raises `ValueError`); HYDRAFloods 2023.10.14 still passes the deleted `Dataset(rescale=...)` keyword, handled by a producer-only compatibility shim; `hf.country_bbox("Malaysia")` returns LSIB *bounds*, spanning peninsula **and** Borneo — 144× Klang Valley box, mostly sea, on workflow that already takes days; and HYDRAFloods appends `_water` to the daily base path, so the reader expects `daily_water_YYYYMMDD_water` and the transformation is pinned by test. Layer may declare `requires_env`, checked *before* `ee.Initialize()` for same reason date is: configuration gap must not report itself as authentication failure.

**Layers are a shared engine plus peer domains, and soil never lives in `flood/`.** `tiles/engine.py` owns the `Layer` record, date and sensor validation, map-id minting, the cache and the tile-access probe, and knows nothing about any dataset; `tiles/ee_session.py` owns the Earth Engine session and raises `LayerUnavailable`. `flood/` and `land/` are peers — neither imports the other (asserted by parsing land's imports, not grepping its prose, which mentions flood on purpose), both import `tiles`, and each has its own catalogue, route (`/flood/*`, `/land/*`), fixture and panel instance. One component, `LayerPanel`, renders twice on `group`. The split was worth its refactor because two couplings inside the old `tiles_for` were already latent bugs: `import hydrafloods` was unconditional, which would have made every soil layer fail on a machine needing only `earthengine-api`, and `parse_sensor` validated against the flood sensor list rather than the layer's own. The `land` layers inform MCMC MTSFB TC G041:2023 §6.3.2 (soil) and §6.3.3 (vegetation) and are **context, not risk factors** — `AHP_FACTORS` is unchanged. Four of those duties — compound cracks and subsidence, ponding inside the compound, diesel/oil scheduled waste, and the 1 m perimeter grass cut — have no satellite answer at these resolutions, and the panel says so outright rather than letting a green wash imply compliance. **EVI, not NDVI**: NDVI saturates in dense tropical canopy, and EVI's `+L` term does *not* cancel Sentinel-2's ×10000 reflectance scale the way a normalised difference does — feed it raw DN and every pixel is wrong while the image still renders plausibly (pinned by a test asserting the scaling precedes the expression).

**Fire is observed evidence beside the score, and every hard-won fact about the source is a thing that failed silently first.** `thermal/` is the third peer on `tiles/` (`/fire/layers`, `/fire/tiles/{id}`, `/fire/exposure`), and nothing it returns enters `risk`, `priority`, the decision bands or `attribution` — a hotspot is a 375 m thermal anomaly that can be a plantation burn, a flare or hot bare ground, so giving it an attribution share would let `dominant_factor`'s argmax select an intervention off a satellite's guess at what is warm, which is the failure-label invention `docs/Backend_Handoff.md` §0.6 forbids. It reaches work instead through a reviewed path: `propose_fire_inspection()` is a sibling of `propose_action()`, never a widening of it, keyed by the literal `fire_exposure_inspection` in `actions.yaml`, and its `why` is an evidence sentence rather than an attribution sentence. Four source facts are load-bearing and none of them raises. **`NASA/LANCE/NOAA20_VIIRS/C2` is an `ee.ImageCollection`, not a feature table** — `ee.FeatureCollection(VIIRS_ASSET)` returns a collection of `.size()` 1056 whose `.filter(ee.Filter.eq("acq_date", …))` and `.filter(ee.Filter.inList("confidence", ["n","h"]))` both come back 0 with no error, so anyone writing against the FIRMS *CSV* mental model ships a silently empty layer. **The detection mask must come off `Bright_ti4`**, because `confidence` and `DayNight` are unmasked and 0-filled — 12.7 million zero pixels over the Malaysia bbox alone — so `confidence.neq(0)` would read open ocean as confidence data while dropping every genuine low-confidence detection into the same bucket as it; and for the same reason the window is screened per image and summed, never `.mosaic()`ed (a mosaic pairs each detection with the last image's unmasked confidence and cross-tabs to 94.6% "low" where per-image pairing gives ~3%). **The reduction needs `.unweighted()` AND `crs="SR-ORG:6974"`, and they fix different things.** Weighted, the reducer returns fractional pixel counts (6.71, 11.99) that cannot honestly be called pixel-days; without the native CRS, `reduceRegions` resamples onto a 375 m WGS84 grid and counts a different pixel set — measured over 1,164 towers for 2026-09-07..09-10, the top tower read **38 detection-days without `crs` against 36 with it, and 40 towers carried detections against 41**, at the same runtime. A count of satellite pixels that changes with the output grid is not a count. And **the newest granule is normally yesterday** (measured 2026-09-10, newest `system:index` was `2026252`), so a window ending on the selected day usually holds **2 granules, not 3** — never hardcode or assert 3; only ZERO granules is an outage, and zero *hotspots* is a legitimate quiet answer that must not 503. That distinction runs all the way out: `screen_towers` returns `None` for "we could not ask" and a populated body with `towers: {}` for "we asked and it is quiet", and no tower is ever written with `hotspot_pixel_days: 0`, because a zero reads as a measurement of quiet ground. Measured live on 2026-09-11: snapshot `viirs-2026-09-11-09715ed2147d`, 2 granules, source 18.7 h old, **1,164 towers screened, 7 with detections**, snapshot 5.8 s and full screening 12.1 s.

**The ITU fibre backbone is drawn and measured, and the measurement is why it draws nothing else.** `backhaul/layers.py` is the fourth peer on `tiles/` (`/backhaul/layers`, `/backhaul/tiles/{id}`) and the only one that never reaches Earth Engine — ITU publishes the backbone from its own GeoServer, so it is a `kind="wms"` layer resolved the way `_resolve_glofas` resolves GloFAS, and its catalogue returns `earth_engine: null` both online and offline. It was measured before it was built, against the standing rule that a second opinion earns its place only by beating what is served: over all 1,164 national towers, distance to the nearest operational link ranks `needed_corrective_maintenance` at **ROC-AUC 0.6075**, below `dist_power_m`'s **0.6919** — a column the model already has and with which it correlates **0.386** — and far below the served model's **0.910**. It fails the `detector_auc > model_auc` necessary condition, and **1,009 of 1,164 towers sit within 10 km of a line**, so it is near-constant exactly where dispatch is decided: the shape of the GSW columns dropped at lift 0.99x. Nothing it returns enters `risk`, `priority`, `attribution`, `urgency_days` or the bands, and an AST test fails the build if the module ever imports `model`, `scheduler`, `adapter` or `agent`. The caveat that would matter on revisiting: the maintenance label is synthetic and its generator never saw fibre, so this shows the layer adds nothing to *this* pipeline, not that backhaul is irrelevant to real maintenance — re-run it against real work orders. Three source facts are load-bearing. **The geometry is schematic**: across the 382 links covering Malaysia the median link carries **2 vertices** at **47.6 km median spacing**, so these are straight lines between endpoints and a per-tower distance read off them is a distance to a drawn line, which is why the description refuses that reading in words. **Only one of the four advertised layers is readable** — `trx_geocatalogue` renders, while `range_10km/25km/50km` (the distance-to-node buffers, precisely what a proximity read would want) return `permission denied for table range_10km` as an **HTTP 200 carrying `application/vnd.ogc.se_xml`**; a probe testing the status code would call that a drawable tile, so the resolver reuses the engine's content-type-aware `_probe_wms_access`. And **the source's own default style is unusable**: it selects by geometry type alone and paints point markers and label haloes over everything — measured on one z7 tile, 3,397 black and 1,443 yellow pixels against **six pixels** of the blue line it advertises. `BACKBONE_SLD` ships one `LineSymbolizer` inline as `SLD_BODY` (same tile: 8,934 pixels, all stroke, at `#1d4e89`), which suppresses symbols the source would otherwise paint while inventing no geometry and reclassifying nothing — a style may decide what is legible, never what is true. It stays one rule and one colour although `status` and `type_inf` are right there, because a three-hue key at 47.6 km spacing would invite the per-tower reading the layer exists to refuse; the legend has one row to match and is keyed off `BACKBONE_STROKE` rather than a repeated hex, after a first draft shipped three hues no tile has ever contained.

**Two flood layers, answering different questions.** `floodLayer.ts` paints *attribution share* — how much of model's risk it assigns to flood, averaged per 2 km hex. `inundationLayer.ts` paints *ground*: HAND threshold tiles showing which land sits at or below a chosen water level across Southeast Asia. ASF applies a Remap → Colormap rule per 256 px Web-Mercator tile, avoiding one enormous regional PNG. Its mosaic encodes both valid zero-height floodplain and ocean as zero, so the basemap's own ocean polygons mask the latter without discarding the former. The committed Sunway PNGs remain inputs to the pilot-only 3D volume and its tower rings; the UI states that coverage split. Regional pixels use four derived-depth bins: green 0–<0.5 m, blue 0.5–<1 m, yellow 1–<2 m, and red ≥2 m; 3D uses the same colours on its coarser stage-bucket estimates.

**`maplibre-gl` must stay out of Vite's dep pre-bundler** (`optimizeDeps: { exclude: [...] }` in `vite.config.ts`). MapLibre resolves its Web Worker via `new Worker(new URL(...))`; pre-bundler rewrites that specifier into `.vite/deps/` without emitting chunk, so worker 404s. Failure mode silent and very misleading: all GeoJSON parsing and tiling happens in that worker, so every circle/symbol layer renders empty while raster basemap tiles keep working (they decode on main thread), and `map.on('error')` never fires. Symptom is "map loads fine but has no towers on it". Dev-only — production builds unaffected, so `npm run build` passing proves nothing here. Diagnose with `window.__map` (exposed by `MapView`): `isStyleLoaded()` stuck `false` plus `querySourceFeatures('towers').length === 0` is this bug, not paint or filter problem.

**Crew capacity is a time budget, not a job count.** `policy.yaml` has no `jobs_per_crew_day`; it has a `shift` block (`day_start`, `hours_default`, `min_slot_hours`) and each crew record carries `shift_hours`. `optimize.py` accepts a placement only when `cursor + travel + duration` still finishes inside the shift, where `cursor` is when the crew becomes free and the travel leg is measured **from where the crew actually is** — the depot for the day's first job, the previous tower after that. Two consequences worth knowing before touching the solver: a tight cluster of towers fits more jobs than a scattered one at identical risk, and crews are ranked for a slot by *insertion cost in minutes*, not by depot distance, because mid-route the nearest depot is rarely the cheapest crew. On-site hours come from `duration_hours` in `actions.yaml` (travel is **not** included there — it is derived per leg), falling back to `DEFAULT_DURATION_HOURS` rather than raising, since a default-width bar is recoverable and a 500 is not.

**Every clock figure on the schedule is solver output, and must stay that way.** `ScheduleEntry` carries `travel_min` / `start_min` / `end_min` as minutes from midnight, set in `optimize.py` and surfaced through `schemas.py`. `GanttBoard` derives bar position, bar width, the travel connector and the utilisation percentage from those three numbers alone. This replaced a grid that rendered a hardcoded `['09:00 - 13:00', '14:00 - 18:00', ...]` array indexed by `entry.order` — times that looked authoritative and were not backed by anything. Do not reintroduce a client-side estimate: `lib/gantt.ts` deliberately reports a lane as `untimed` when the fields are absent instead of inventing them. The one exception is the offline fixture, which states its own times as fixture *content* with a flat `FIXTURE_TRAVEL_MIN` and says so in a comment — that is data, not a derivation.

**A pin re-derives its clock; only crew and day are held fixed.** `_resolve_around_pin` seeds pinned entries first, but the seeding loop recomputes `travel_min` / `start_min` / `end_min` / `order` against the crew-day it is landing in. Skipping that would let a pinned job carry the times from whichever slot it held before the planner moved it, and the timeline would then draw a bar the solver never agreed to.

**Reserve is protected absence, and readiness is territorial.** `policy.yaml`'s `readiness` block (`reserve_crew_days` per crew type, `reserve_days` by horizon index, `rotate_reserve`) tells `scheduler/reserve.py`'s `select_reserve()` which crew-days to hold open before the main pass runs; `optimize.py` then runs twice — once with those crew-days blocked, once without — so it can label a placement `reserved` only when the reserve slot is the *reason* it went unscheduled, not just incidentally free. `sla_may_consume_reserve` lets a job whose deadline falls inside the horizon spend a reserve slot rather than miss SLA (`ScheduleEntry.consumed_reserve` marks this); an SLA-driven emergency dispatch into a reserved crew-day is the intended way to spend the slot, and should displace nothing. `ScheduleRun.reserve` (`ReserveSlot[]`) lists only crew-days still free as of that resolve — a slot vanishes from the list once something occupies it, so a reserve count is "remaining," never a configured total. Reserve capacity is protected *absence*: it carries neither a band colour (severity) nor the accent (chrome/control) — `lib/reserveHatch.ts`'s `RESERVE_HATCH_STYLE`, a neutral `overlay`-token hatch, is the one definition every reserve mark (`ReserveBand`, `ReserveDetail`, `WeekStrip`, `ScheduleGridByTower`'s day-column header) draws from, replacing an earlier duplicate that lived hardcoded in `WeekStrip` alone. `ReadinessBar` states the same idea in the PageHeader without the hatch (per-team reserve chips, cool accent, never the warm severity triad).

**The crew view shows one day; the by-site view shows the week.** An hour axis cannot hold seven days without becoming unreadable, so `selectedDay` lives in the store and `WeekStrip` exposes it — one tab per `run.horizon` entry (not a hardcoded day count), each with a job count and a load bar whose hatched remainder is reserve still free that day. `TimelineBoard` further groups the selected day's bars by `crew.crew_type` (`RoleGroup`, `ROLE_TEAMS` order) so the four capabilities read as separate pools instead of one flat crew list. `select()` keeps `selectedDay` in sync with whatever was just selected, so the board never holds a selection on a day it is not displaying. Selection is `{kind: 'job', crew_id, day, tower_id}` (plus `'free'`, `'reserve'`, `'emergency'` variants) — not the old `{crew_id, day}` — because a crew-day can hold more than one bar and a crew-day selection alone cannot say which one. `ScheduleGridByTower` ("By site" in the UI; the component and `viewMode: 'tower'` keep their old names) stays a day-column grid on purpose: a tower takes at most one job per day, so a time axis would buy nothing. It renders its own reserve marker in the day-column header, not per tower cell — `run.reserve` is a per-crew-day slot, not a tower row, so marking an empty cell would falsely imply that tower is reserved.

**The ticket -> schedule hand-off is a flag, and only two actions may move a ticket through it.**
Picking the Assignee Agent on an **open** ticket makes `state/useAutoDispatch.ts` set
`schedule_pending`; that is the entire hand-off, and it deliberately dispatches nothing. The
Schedule side (`TicketApprovalStrip` in the Ranger dock -> `TicketApprovalPanel` in `DetailPanel`)
suggests a crew, previews the cost, commits through the ordinary `/schedule/pin`, and only then
calls `markScheduled(ticket_id, crew_id)`; rejection or a failed commit calls
`markScheduleFailed()`. **Never move a ticket through this flow with `setStatus`/`assignCrew`** —
those are the manual paths and the drawer's status strip reads them differently. Full contract in
`docs/Ticket_To_Schedule_Handoff.md`.

The guard is `agent_id === 'assignee_agent' && status === 'open'`, and **three different controls
assign a crew while only one of them satisfies it**. `TicketCard`'s sparkle picker and the drawer's
"Send to Schedule for approval" button call `setAgentId`; the drawer's Assignee dropdown and the
suggested-crews "Assign" button call `assignCrew`, which flips `open -> active` and so
*permanently* disqualifies that ticket — nothing visibly fails, the ticket simply never appears on
the Schedule side, and re-picking the agent afterwards cannot rescue it. `useAutoDispatch` carries
a `import.meta.env.DEV` table naming the missing precondition per ticket; read it before
suspecting the Schedule side.

**Ticket tower ids are real, and fixture lookups silently return nothing for them.** Tickets are
raised against the live population (`createEmergencyTicket` draws from `useLiveTowers`), so a
`tower_id` looks like `MY_N10736133691`, not the `MY_1000`-`MY_1043` of `fixtures/towers.ts`.
Anything resolving a ticket's tower must use `useLiveTower(tower_id, weights)`. The same holds for
crews at a different scale: `fixtures/crews.ts` holds **12** crews across 3 territories while
`config/crews.json` rosters **30** across all 16, so ranking against the fixture cannot offer the
crew the solver would actually send. `lib/ticketSkills.ts::rankCandidateCrews()` keeps both
fixtures only as fallbacks for older call sites — pass `{ tower, crews }`. Measured: ranking one
Penang ticket against the fixtures returned **0** candidates (the tower lookup failed outright);
against live data, 2.

**An override re-solves against its own run's anchor, not the demo clock.** `/schedule/optimize`
is anchored to whatever `today` the frontend sends, but `preview`/`pin`/`emergency` used to leave
`today=None`, which `Optimizer.optimize` defaults to `policy.yaml`'s fixed `demo_clock.today`. Any
override therefore snapped the horizon back to that date, and the day a dispatch had just been
placed on read as "outside the current planning horizon" on the very next render.
`api/routes/schedule.py::_anchor(run)` returns `horizon[0]` — which *is* the run's resolved today,
since `_horizon()` starts there — and all three routes pass it. `agent/tools.py`'s
`optimize_schedule_tool` still does **not**, so an agent-driven re-optimize shifts the whole board's
dates; that is a known gap, not a design.

**Override endpoints accept any tower, not just the maintain band.** `/schedule/optimize` proposes
work orders only for `decision == "maintain"`, so `work_orders_by_tower` has no entry for a
watch/ok tower — and a ticket can be filed against any tower at all. Pinning one used to raise a
bare `KeyError` (a 500, and because Starlette drops CORS headers on an unhandled exception, it
reads in the browser as a CORS failure rather than a server error).
`api/routes/schedule.py::_resolve_work_orders()` synthesizes the missing work order and tower
record, preserving `override.py`'s own documented "never blocked" contract. Reuse those three
routes rather than reimplementing pin logic, or the crash comes back.

## Known defects (verified, not yet fixed)

Recorded so not rediscovered from scratch, and so symptom not misattributed to code working correctly.

- **Fixture place names contradict fixture coordinates.** `fixtures/schedule.ts` `PLACE_NAMES` labels scheduled towers with Kelantan towns (`MY_1042` = "Gua Musang"), while `makeScoredTower` in `fixtures/towers.ts` places every scored tower inside `SUNWAY_BOUNDS` in Selangor. Anything plotting tower next to its name shows contradiction — why `RouteMap` labels stops by `tower_id` rather than calling `placeName()`.
- **`ScheduleEntry.order` almost always 1 in offline fixture** (13 of 14 entries), so any route or sequence UI must look deliberate with single stop rather than assuming multi-stop routes. Multi-stop routes appear only from live optimizer.
- **A dispatch into a territory you are not viewing is invisible, and looks like a no-op.** The
  board and the week strip's job counts both read `useTerritoryRun()`, i.e. one territory's crews.
  Approving a Johor crew while the selector says Selangor books a real crew-day that draws no lane
  and moves no count — the planner correctly reports that nothing happened. `TicketApprovalPanel`
  now points the selector at the proposed crew's territory when its panel opens; anything else
  that books cross-territory needs the same courtesy.
- **A cross-day move cannot be shown on the crew timeline.** `TimelineBoard` draws a single
  `selectedDay` on an hour axis, so a job moving `Sat 12 -> Thu 10` does not slide — it vanishes
  from one day and reappears in another. `ScheduleGridByTower` ("By site") is the only view holding
  the whole horizon, so it is the only place a rearrangement can be animated.
- **Ranger's no-API-key parser turns any 4-digit number into a tower id.**
  `agent/tools.py::apply_constraint` regexes for `\d{4}` plus a trigger word ("emergency", "today",
  "dispatch now", "send someone"), so a message mentioning ticket `T-1038` is parsed as an
  emergency dispatch to `MY_1038` — a different, unrelated tower. Worse, `ParsedConstraint.to_pins()`
  returns `[]` unconditionally, so `emergency_dispatch` pins nothing: the turn just re-optimizes the
  whole board (with the wrong date anchor, above), which reads as dozens of unexplained
  reassignments. Any text seeded into the composer must avoid those trigger words, or sending it
  silently replaces the schedule.
- **On live Sunway AOI the timeline shows one bar per lane, and that is correct.** Every maintain-band tower there resolves to flood work (`duration_hours: 4`) against two Selangor civil crews, and two four-hour jobs plus travel do not fit eight-hour shift — so solver books one per crew-day and leaves rest unscheduled. Multi-bar lanes with visible travel connectors do appear: on offline fixture, and on any AOI with mix of shorter work orders. Do not "fix" this by shortening `duration_hours` to make demo look busier.

### Fixed, recorded because the cause is not findable from the symptom

- **The Python package is `thermal/`, not `fire/`, and an `__init__.py` would have been the worse fix.** `fire` 0.7.1 (google/python-fire) is installed in this venv as a **hydrafloods dependency**, and a regular package with `__init__.py` beats a PEP-420 namespace portion regardless of `sys.path` order — so `src/backend/fire/` could not be imported at all (`ModuleNotFoundError: No module named 'fire.exposure'`) no matter where the backend root sat on the path. Forcing it to win by giving it an `__init__.py` would then have shadowed python-fire for `hydrafloods` and `simplecmr/cli.py`, breaking the **radar flood layers** silently and only once Earth Engine was actually reached — a failure two packages away from the edit that caused it. Hence `thermal/`, named for what the sensor measures, with everything user-facing unchanged: routes `/fire/*`, `api/routes/fire.py`, `Layer.group == "fire"`, the frontend `LayerGroup` member `'fire'`, `fixtures/fireLayers.ts`. A test asserts `screen_towers`/`snapshot_for` resolve as `thermal.*` and that nothing under `src/backend` imports a top-level `fire`. **The next person adding a domain package will hit this** — check the venv for the name before claiming it.
- **Overrides re-solved against the demo clock instead of the run's own day.** `/schedule/preview`, `/pin`, `/emergency` and `/why` never passed `today=`, so `Optimizer.optimize` fell back to `policy["demo_clock"]["today"]`. Measured: a run optimised for **2026-09-09** came back from `POST /schedule/pin` with its horizon reset to **2026-08-17..08-23** and the pinned entry — still on 2026-09-09 — the only entry outside the horizon it was returned with, so `WeekStrip`, which tabs from `run.horizon`, could not draw the very job the planner had just pinned. Fixed by `_run_today(run) = date.fromisoformat(run.horizon[0])`, threaded through all four; `None` for a run with no horizon, which leaves the demo-clock default standing for exactly the case it was written for.

## Project-specific rules that affect code changes

- **Never fabricate failure label or expose failure-probability semantics.** System schedules maintenance *need* and *urgency*, not predicted failure events (`docs/Backend_Handoff.md` §0, `docs/Concept_Overview.md` §5). Endpoint names, docstrings, UI copy must stay consistent.
- **Optimizer decides; LLM never does.** Any change to `agent/` must preserve: model calls tools and reports tool output verbatim, and `optimize_schedule` output never re-described in model's own words.
- **`/schedule/preview` must never mutate stored state** — only `/schedule/pin` commits. Separation load-bearing for override UX.
- **Config over code** for scheduler behavior: crew roster, action mapping, policy thresholds live in `config/*.{json,yaml}`, not literals in `scheduler/*.py`.
- **Unscheduled/displaced work always returned explicitly**, never silently dropped (applies to `optimize.py` and emergency insertion in `override.py`).
- **Band colour has exactly one source: `src/frontend/src/lib/colors.ts`.** Map layer, console's `BandModule`, `SelectionHud`, `TowerDrawer` and schedule grids all import from it. `towerLayer.ts` previously carried own hardcoded triad and drifted, so map rendered towers in different colours than legend explaining them.
- **Two controls say "area" and they are not the same control.** `AreaModule` filters by `territory`: it hides towers outside one ADM1 state, frames them with `fitBounds`, and changes nothing about their scores. The framing lives in the click handler, not an effect on `areaFilter` — `useLiveTowers` returns a fresh array identity on most renders, so an effect would re-fly the camera on unrelated ones. Its padding is asymmetric (left 276, bottom 150) because the console's modules float **on** the map, so a symmetric fit centres a territory underneath this very panel; each side is clamped to a share of the canvas so a narrow window loosens the fit instead of asking fitBounds to solve a negative viewport. `maxZoom` is 11, below the 12.5 icon gate, so two-tower Perlis frames as dots rather than dropping into street zoom. `AoiModule` sends the live viewport to `POST /score`, which re-filters the feature table and **re-cuts the decision bands for that extent**, so the same tower can change band. Both are legitimate and the footer copy on each says which it is; conflating them would let a planner read a re-banded AOI as a national ranking. Band and area are ANDed into one MapLibre expression by `towerFilterExpr`, deliberately not two `setFilter` calls — `setFilter` replaces rather than merges, so applying them separately makes whichever ran last silently win while the other appears inert.
- **Map's two tower layers move together.** `towers-layer` (coloured circle halo) carries band/risk signal; `towers-icon-layer` (tower PNG) is decoration on top, shares same source. Any filter applied to one must apply to both, else band-filtering leaves icons floating with no halo underneath. Icon PNG is raster, not SDF, so `icon-color` cannot tint it — band colour lives on circle and must stay visible under icon (`docs/Tower_Icon_Layer_Plan.md`). Decoration must never outrank data: with `icon-allow-overlap`/`icon-ignore-placement` both `true`, MapLibre skipped collision culling entirely and ~130 icons stacked into confetti burying band colours at AOI zoom. Culling only thins decoration — halo is circle layer, never collides, so every tower keeps its reading.
- **Map's zoom bands hand off to each other, each gate has exactly one definition.** Hillshade relief fades *out* across z10→z12.5; tower icons fade *in* across z12.5→z13.5. Relief informative where Titiwangsa range is and terrain actually varies; icons legible only once towers far enough apart. `TOWER_ICON_ZOOM_GATE` exported from `towerLayer.ts` because `MapView` re-applies `icon-opacity` (multiplied by score-opacity slider) and previously inlined second hardcoded copy of curve — editing gate in one place looked correct until someone touched slider, which reverted it.
- **3D is a mode, and readouts were fixed before it was allowed on.** `useMap3D` tilts camera, calls `setTerrain` on DEM `terrainLayer.ts` already loads, raises `flood-volume-extrusion`. Three things had to become true first. Graticule is now **projected polylines** (`graticuleGeometry`), not CSS fractions: fraction assumes longitude maps linearly to screen x, which tilt destroys — same rework fixed standing bug where lines sat at true fractions while labels spread with `justify-between`, so two only agreed by luck. Scale rule stays **closed form at map centre**, labelled "at centre" when pitched; measuring with `unproject()` looks more rigorous and is wrong, because with terrain on it returns where ray hits MESH, so at high exaggeration two pixels either side of centre strike nearly same point on steep face — z15 view measured 0.2 m/px against true 4. And **terrain and water share one exaggeration factor**: stretching them differently would not exaggerate scene, would falsify depth of water relative to ground it covers. Factor never silent — HUD prints it, because 5 m of water across 14 km AOI is 0.035% of frame and any readable 3D flood is exaggerated one. Defaults to ×10 not ×20 after looking at both: tower AOI carries 82 m of real relief (SRTM −22 m to 60 m), and ×20 renders coastal plain as alpine range, stronger falsehood than flat map. Known artefact: DEM holds small negative values over water (Sunway's flooded tin-mining ponds), which exaggeration turns into pits.

**Depth carried in height AND colour.** `WATER_DEPTH_BANDS` is the shared source for the ArcGIS tile rule, 3D paint, and 3D key: green 0–<0.5 m, blue 0.5–<1 m, yellow 1–<2 m, red ≥2 m. They are scenario-depth display bins (`stage - hand`), not calibrated hazard classes; numeric labels are mandatory because three hues also appear in tower decision bands. Both 3D paint properties bake stage in as literal, so **both must be re-set when stage changes** — updating only `fill-extrusion-height` leaves `fill-extrusion-color` computing against whatever stage layer was created with, which ships as water whose colour means nothing. That shipped once, why depth legend exists: colours with no key are decoration.

**3D water is vector, geometry derived from 2D masks.** MapLibre extrudes geometry, never rasters — raster draped on terrain follows ground and shows no volume, the one thing 3D is there for. `data/prepare_flood_volume.py` reads committed stage PNGs, and because they are strictly nested (asserted, not assumed) the stack encodes only the first stage bucket at which each cell turns wet (`0.5/1/2/3/5`), not continuous HAND. So one 419 KB GeoJSON carries every stage and `h - hand` is a banded lower-bound depth estimate, computed client-side; exact 3D depth would require regenerating geometry from continuous HAND. Volume drawn only when 3D on: seen from directly above, extrusion is edge-on and merely duplicates raster beneath.

**Relief is `hillshade` when 3D is off, and then the camera stays top-down.** `terrainLayer.ts` adds keyless AWS/Tilezen terrarium DEM below every tower layer; `setTerrain` is called only by `useMap3D` (see the 3D rule above, which is where the pitch story lives — the readouts were reworked before tilt was allowed on, so this is no longer a prohibition). What still holds: **the flat path must stay flat.** Anything that pitches the camera outside `useMap3D` re-breaks the graticule and the scale rule, because the closed-form maths in `lib/graticule.ts` assumes an unpitched view and only the 3D path compensates for it. Hillshade's default `accent-color` is blue cast and is neutralised, because cool accent already means "interface chrome" on this screen. Under light theme relief inverts: on Dark Matter shading carried by lifted highlight against near-black shadow, whereas on Positron the tiles *are* the highlight, so shadow does the work and highlight goes white.
